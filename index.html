What everyone assumed

Six production problems. In each one, the whole team had already agreed on the wrong cause — or hadn't seen there was one. The last one you can run yourself.

Symptom

None visible. That was the problem — 2,000+ bikes and 180+ stations running 1,200+ swaps a day, and no way to tell a legitimate swap from a fraudulent one.

Assumed

That losses were noise in the margins. There was no labelled fraud set, no baseline, and nothing to compare a bad swap against.

Root cause

The signal was already in the telemetry, uncorrelated. I designed an extensible rule engine from production data, correlating four to five telemetry signals per transaction.

Result

Gave operations its first quantified view of fleet-wide fraud, measured by 33,000+ swaps screened in two weeks — 30+ cases confirmed, 600+ flagged for review. Automated warning notifications are the next layer in build.

Symptom

A Partner API architecture, planned and approved, about to go into build.

Assumed

That the design was settled. Nobody had costed what it would do to the run-rate.

Root cause

The data flow it specified would have carried a projected 80–85% higher cloud run-rate. I raised it unprompted and re-architected it as a dual-mode pull/push service in FastAPI across EC2 and Azure Event Hubs, with retry caching and lookup-table optimisation.

Result

Avoided a projected 80–85% higher cloud run-rate, by replacing the design before a line of it was built — delivered in three days against a three-week estimate.

Symptom

Co-located services starved of CPU, unable to execute reliably on a box a core service was quietly dominating.

Assumed

Everyone had a favourite suspect. Optimisation targets were being picked from intuition, not measurement.

Root cause

Nobody had sampled the box over time. I built a pidstat watcher sampling across three separate days and time windows, which named the real offenders and moved the team from assumption-based targets to data-driven ones.

Result

Cut the core service from 40% average and 65% peak CPU to 1.1% and 6.7%, freeing the co-located services that had been starved.

Symptom

Three to four emergency production restarts every week, indefinitely.

Assumed

Load. Restarting the box had quietly become part of the team's routine.

Root cause

A file-descriptor leak in a hot path — found by auditing the full code path, accelerated by an internal AI code-analysis agent I built for the job.

Result

Eliminated 3–4 emergency restarts a week, with zero recurrences since, by shipping the fix overnight.

Symptom

EC2 disk exhausted. Co-located Python services starving. Data being lost.

Assumed

The instance was undersized. Add disk, move on.

Root cause

Runaway SQLite WAL growth driven by incorrect checkpointing and write patterns.

Result

Recovered 19 GB of disk and stopped the data loss, by correcting the checkpointing and adding a scheduled disk-audit script emitting structured diagnostics for automated triage.

Symptom

A long-standing performance complaint on the platform's heaviest views.

Assumed

A front-end problem. Therefore, the front-end team's problem.

Root cause

Two independent causes: unbatched backend queries, and re-rendering component trees behind an oversized bundle. Profiling found both.

Result

Restored responsiveness on the platform's heaviest views, measured at ~40% faster request paths, by fixing both sides of the handoff myself rather than passing half of it back.
